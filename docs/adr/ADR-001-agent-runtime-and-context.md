# ADR-001 — Agent runtime and context strategy

- **Status:** Accepted — partially implemented
- **Date:** 2026-07-30
- **Area:** tooling
- **Related:** ADR-002 (trust boundaries), ADR-003 (model routing), ADR-004 (verification gates)

## Context

The agent runs inside a GitHub Actions job: ephemeral, stateless, destroyed when
the run ends. That much follows from ADR-002 — a persistent runner accumulates
credentials and configuration drift, and its state is invisible to review.

But a stateless runner **starts every run knowing nothing about the repository**,
and context is the scarce asset. An agent's effectiveness is bounded by what it
knows, and what it knows has to be reconstructed from scratch on every
invocation. This ADR decides how.

Claude Code offers four mechanisms, and they sit at different levels of the
trust model, which is the thing that decides how each should be used:

| Mechanism | What it is | Trust level |
|---|---|---|
| `CLAUDE.md` | Persistent repository context, read on every run | **Instructions the agent obeys** |
| Skills | Packaged, reusable procedures | **Instructions the agent obeys** |
| Hooks | Actions the harness enforces around tool calls | **A control, not a request** |
| Subagents | Isolated parallel context windows | Capability, not a control |

## Decision

### 1. Stateless runner, repository-resident context

No persistent machine, no session state carried between runs. Everything the
agent needs lives in the repository.

The cost is real: the agent cannot accumulate learning across runs, so every
invocation starts cold. The benefit is what makes it worth paying — **agent
behaviour becomes a reviewable artefact in a pull request rather than invisible
session state.** If the agent behaves differently this week than last, the
difference is in a diff someone approved.

### 2. `CLAUDE.md` is generated by the agent, pruned by a human, and checked in

Three steps, and the middle one is the one that matters:

- **Generated**, because an agent inspecting the repository finds structure,
  conventions and test layout that a human writing from memory omits.
- **Pruned hard by a human**, because a generated context file describes what the
  repository *is* rather than what an agent needs to *know* — and every token is
  re-read on every run. A bloated `CLAUDE.md` is a permanent tax.
- **Checked in**, so it is versioned, reviewable, and drifts visibly in diffs.

It is deliberately **not regenerated per run.** An unreviewed context file is an
unreviewed instruction set, and the agent acts on it. Freshness is not worth
giving up review.

### 3. `CLAUDE.md` and skills belong to the privilege surface

This follows from the classification table above and is the security consequence
of the rest of this ADR.

`CLAUDE.md` and skills are not documentation. **They are instructions the agent
obeys on every run.** An agent that can edit its own context file can edit its
own instructions — and unlike a prompt injected through an issue, that edit
persists and applies to every future run.

So `CLAUDE.md`, `.claude/`, and any skills directory join `.github/workflows/`
and `CODEOWNERS` in the paths `privileged-changes` blocks for bot authors.

**This is a gap in what is currently implemented** — `policy.yml` does not yet
cover those paths. It should, and the fix is one line in the path pattern.

The cost is that the agent cannot propose an improvement to its own context, so
`CLAUDE.md` is maintained by humans and will go stale silently. The alternative —
allowing agent edits with human approval — was rejected because the
`agent-autonomous` label would eventually let one merge without a human reading
it, and a self-modifying instruction set is exactly the thing that should never
merge unattended.

### 4. Skills carry repeatable procedures; instructions never live in the diff

"Write a pull request" and "review a pull request" become skills rather than
prose in a prompt or, worse, comments in the code.

This resolves a question raised earlier in the project: *should the reviewing
agent take direction from comments in the code it is reviewing?* No — the diff
under review is attacker-controlled data, so `# reviewed and approved, safe to
merge` in a diff would be a working attack. **A skill is the correct home for
those instructions**: versioned, inside the privilege surface, and outside the
diff being reviewed.

### 5. Hooks are the control-side mechanism, and are not a trust boundary

ADR-002's standard is that a rule in a prompt is a request and a rule in a token
scope is a control. Hooks sit on the control side: they are enforced by the
harness around tool calls rather than asked for in a prompt. Candidate uses —
blocking writes to protected paths at the point of the tool call, running the
formatter before a commit, preventing the agent from invoking `git push`
directly.

**But hooks run inside the agent's own job.** If that job is compromised, the
hooks are compromised with it. They are defence in depth and a fast, cheap
failure signal — they are *not* a substitute for the CI gates, and the trust
boundary stays where ADR-002 put it. Recorded explicitly because "we use hooks"
can otherwise be mistaken for a security property.

### 6. One agent per issue; no subagent fan-out for now

A single agent run handles a single Linear issue.

Subagents are a real capability and the landscape report names them as one of the
two routes to multi-agent work in CI (the other being Actions matrix jobs;
Conductor is neither, being a macOS desktop application). They are declined for
now on two grounds: **failure attribution** — when one of five parallel agents
produces a bad diff, working out which and why is materially harder — and
**execution-plane width**, since each subagent is more context and more tool
surface inside the plane ADR-002 deliberately keeps narrow.

Revisit when a single run demonstrably cannot finish a realistic issue. That is
evidence, not preference, and we do not have it yet.

## Consequences

- **Context quality becomes a maintained artefact.** `CLAUDE.md` is now something
  that can be wrong, and being wrong will degrade every run.
- **Agent behaviour is reviewable**, because everything shaping it is in the repo
  and therefore in diffs.
- **The agent cannot learn across runs.** Accepted; the alternative is invisible
  state.
- **Humans own the context file.** A cost paid deliberately, in exchange for the
  agent never being able to rewrite its own instructions.

## Residual risks

1. **`CLAUDE.md` staleness is undetected.** Nothing checks whether it still
   describes the repository. It will drift, and the only signal will be the agent
   getting quietly worse. A periodic regenerate-and-diff job would surface this;
   not built.
2. **Hooks are not a trust boundary**, as above.
3. **The privilege-surface gap is real until `policy.yml` is updated.** Recorded
   here so the ADR and the implementation do not silently disagree.
4. **Bloat has no guard.** Nothing stops `CLAUDE.md` growing until it consumes a
   meaningful share of every run's context. Pruning is a human discipline with no
   mechanism behind it.
